# ロータリーエンコーダーの反応確認

現在の恒久設定は、実機用`hardware/lyra-zero-w/gpio.csv`のCLK・DT・SWに
`debounce_us=1000`を指定し、GPIOの監視開始時にOSへ適用する構成です。
gar-toolsの番号判定は元のrequest全体の`seqno`方式へ戻しました。
この構成で通常の顔アプリの右10回・左10回・押下1回を確認し、再起動後の再適用も確認しました。
以下は調査と初期回避策を含む履歴で、末尾に恒久対応を記載しています。

2026-10-31、Luckfox Lyra Zero Wで「回すと時々しか表情が変わらない」を再現しました。
押さずに右10クリック、左10クリックを約1秒間隔で回し、最後に1回押す操作で比較しています。

| 確認 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 右回転をアプリが採用 | 1 / 10 | 10 / 10 |
| 左回転をアプリが採用 | 1 / 10 | 10 / 10 |
| 押下 | 1 / 1 | 1 / 1 |
| 利用者の表示確認 | 時々変化 | 毎クリックで変化 |

## 初期の原因切り分けと互換回避策（現在は置換済み）

GPIOイベント112件を記録したところ、request全体の`seqno`には飛び・重複が46箇所ありました。
一方、端子ごとの`line_seqno`には欠落がなく、信号の並びから右10回・左10回すべてを復元できました。
修正前の読取処理はrequest全体の番号の不連続を検出するたびに途中の回転を捨てていました。
この本機のカーネルと読取処理の組み合わせによる誤判定が、今回の主因です。

ここで確認したのは、回転が採用されない直接の原因です。OSからの`read()`直後、
gar-toolsの欠落チェックや回転判定をする前に、受信した`seqno`はすでに不連続でした。
gar-toolsが計算するクリック数`counter`と、OS由来のイベント管理番号`seqno`は別の値です。
`counter`は採用した回転ごとに±1ずつ更新されます。

gar-toolsの汎用読取を修正し、端子ごとの`line_seqno`で本当のキュー欠落を判定します。
本当の欠落を無視する変更ではなく、欠落時に途中の回転を破棄する処理は維持しています。
接点の揺れは既存の4遷移デコーダーで処理します。配線、SPI速度、表情アプリはこの修正で変更していません。

この変更は、有効な回転を誤って捨てることを避ける互換回避策です。
OS由来の`seqno`の飛び・重複を発生させる仕組み自体を修正したものではありません。
SDKの割り込み処理とイベント生成の間で番号の対応が崩れる可能性を調べていますが、
実行中カーネル内の発生経路はまだ確定していません。

修正コミットは
[`e97fbca`](https://github.com/ThousandsOfTies/gar-tools/commit/e97fbca51bdee499893f6df2c8eaac2f94a9c225)です。
GPIOイベントの仕様は[Linux GPIO v2の資料](https://docs.kernel.org/userspace-api/gpio/gpio-v2-line-event-read.html)を参照してください。

## 検証と範囲

既存の回転・逆回転・接点の揺れ・不完全な回転のテストに加え、実機記録の20クリック再生と、
端子ごとの欠落・最初の読取前の欠落・32ビット番号の周回をテストしました。
ARMv7版をビルドし、実機の顔アプリで20クリックすべてと押下を記録しました。
利用者も毎クリックの表情切替を確認しました。
共有リポジトリの[自動検査とビルド](https://github.com/ThousandsOfTies/gar-tools/actions/runs/41165495253)も通過しました。

約1秒間隔の20クリックでの確認結果です。高速連続回転の追従限界を測定した結果ではありません。
記録は`artifacts/rotary-irq-edges.log`、`rotary-irq-app.log`、`rotary-fixed-app.log`と
`artifacts/rotary-response-report.json`にあります。

## 番号不連続の発生元の追加確認

2026-10-31、gar-toolsのGPIO読取・回転判定を外し、SDKに同梱されたLinuxの
`tools/gpio/gpio-event-mon`で同じ端子のイベントを直接記録しました。
顔のSPI出力は動かしたままです。監視ツールの変更は、ログの行単位出力、
同じpull-upの要求、同じ64イベントバッファの指定だけです。イベントの採番・解釈は変更していません。

| 観測 | 結果 |
| --- | ---: |
| 受信イベント | 158件 |
| request全体の番号の不連続 | 69箇所 |
| 上記のうち同じ番号の重複 | 2箇所 |
| 端子ごとの番号の欠落 | 0箇所 |
| 記録区間のGPIO割り込み数の増分 | 296回 |
| 受信イベントの時刻逆転 | 0箇所 |

番号の不連続は、gar-toolsの回転計算・欠落チェックを外しても再現しました。
今回の記録では、gar-tools内での回転計算がOS由来の番号を飛ばしたという説明は当たりません。
端子ごとの受信番号は連続しており、ユーザー空間の読取待ちキューからの欠落を示す記録もありません。
SDKではrequestの番号を主に割り込み処理で進め、端子番号をイベント生成処理で進めています。
割り込み数と通知イベント数が一致しない経路が関係すると考えられますが、
動作中カーネル内部の個別の実行順序は未追跡です。

この検査は番号の発生元の切り分けです。共有ライブラリーの回避策を、
カーネル側の番号不連続そのものを解消した根治修正と扱わないことを明記します。
監視終了後は通常サービスへ戻し、修正版の顔アプリの起動を確認しました。
記録は`artifacts/kernel-gpio-monitor.log`、`kernel-gpio-monitor-analysis.json`、
`kernel-gpio-monitor-irq-before.log`、`kernel-gpio-monitor-irq-after.log`、
監視ツールの変更内容は`kernel-gpio-monitor-adaptations.patch`にあります。

## GPIO入力のデバウンス設定による比較

2026-10-31、同じSDK監視ツールへ`-b 1000`を指定し、Linux GPIO v2の
`debounce_period_us`を1000µsに設定して比較しました。右10クリック・左10クリックを
約1秒間隔で回し、最後に1回押す検査です。採番や回転判定のコードは変更していません。

| 観測 | デバウンスなし | 要求値1000µs |
| --- | ---: | ---: |
| CLK・DTの通知 | 158件 | 80件 |
| 全体番号の不連続 | 69箇所 | 0箇所 |
| うち同じ番号の重複 | 2箇所 | 0箇所 |
| 端子番号の欠落 | 0箇所 | 0箇所 |
| 信号から復元した右回転 | 10回 | 10回 |
| 信号から復元した左回転 | 10回 | 10回 |

デバウンスありの通知は、20クリック×4変化の80件と押下・解放の2件で計82件でした。
この検査では、GPIO入力層の標準設定で短い変化を抑えることで、
全体番号の不連続がないイベント列を取得できました。入力設定を先に評価すべきだったと整理します。

本SDKのRockchipドライバーは個別端子のハードウェアデバウンス要求に`-ENOTSUPP`を返し、
GPIO cdevはカーネル内のソフトウェアデバウンスへ切り替える実装です。
今回も割り込みは292回（回転用290回・SW用2回）発生しており、
電気的な揺れや生の割り込み自体をハードウェアで減らしたという結果ではありません。
`1000µs`は要求値で、実際の処理時間はカーネルのタイマー精度・スケジューリングにも依存します。

比較後は通常サービスへ戻しました。この時点では検査用の一時設定であり、
通常アプリのCSV／共有コードにはデバウンス設定をまだ追加していません。
通常アプリは前段の端子別番号を用いる互換回避策のままです。
恒久対応では、GPIO標準のデバウンス設定を構成から渡し、元の全体番号による欠落判定を
維持して動作するか確認する方針です。高速回転の追従限界は未測定です。
記録は`artifacts/kernel-gpio-debounce-1000.log`と`kernel-gpio-debounce-1000-analysis.json`にあります。

## 恒久対応：GPIOデバウンスと元の番号判定

2026-10-31、Productの実機用CSVへ`debounce_us`列を追加し、
`encoder_a`・`encoder_b`・`encoder_sw`に`1000`を保存しました。
共通アプリのCSV読込と入力アダプターが値を共有読取の`--debounce-us 1000`へ渡します。
共有読取は`GPIO_V2_GET_LINE_IOCTL`で端子を確保する際に、
`GPIO_V2_LINE_ATTR_ID_DEBOUNCE`属性としてOSへ要求します。
ドライバー本体やメーカーのGPIO設定ファイルに数値を固定する方式ではありません。
設定のないProductとシミュレータは従来どおりデバウンスを要求しません。

gar-toolsの端子別番号による回避策とその専用ファイルを削除し、
元の`last_sequence`と`event.seqno`による欠落判定を復元しました。
初期コミットと現在の`rotary_input.c`を比較し、差分が任意のGPIOデバウンス設定に
限定され、元の番号判定のコードが一致することを確認しています。

| 通常の顔アプリでの検査 | 結果 |
| --- | ---: |
| 右回転 | 10 / 10 |
| 左回転 | 10 / 10 |
| 押下 | 1 / 1 |
| 利用者の確認 | 毎クリックで表情が切り替わり、押下にも反応 |
| 再起動後の入力プロセス | `--debounce-us 1000`を付けて自動起動 |
| 再起動後の初期化 | GPIO ready・液晶の初回フレームを確認 |

共有読取の設定・デコーダーテスト、共通アプリ6テスト、Product2テストと
[共有リポジトリの自動検査・ビルド](https://github.com/ThousandsOfTies/gar-tools/actions/runs/41186962418)を通過しました。
高速回転での追従限界は今回測っていません。1000µsは要求値であり、
カーネルのソフトウェアフィルターが使われるため、実際の安定待ち時間は
タイマー精度とスケジューリングに依存します。
